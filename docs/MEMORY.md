- 2026-11-03: VPN gotchas learned the hard way. (1) OpenVPN 2.7 tries kernel DCO and a rootless container cannot, so the server answers AUTH_FAILED with `dco_new_peer ... Operation not permitted` in its log: the gateway config has `disable-dco`; client containers in tests need `--disable-dco` too, real clients do not. - 2026-11-03: VM runtime lessons (all learned on real images in ~/Downloads, KVM works there). (1) VirtualBox exports configure `enp0s3`; QEMU's default PCI layout names the NIC `ens3` (ACPI slot naming) and the guest never gets DHCP: NIC at `addr=0x3` plus `-global PIIX4_PM.acpi-root-pci-hotplug=off` (the bridge-support property alone does not do it). Find a guest's expectations by mounting the base read-only: `sudo modprobe nbd max_part=8; sudo qemu-nbd -r -c /dev/nbd0 base.qcow2; sudo mount -o ro,noload /dev/nbd0p1 /mnt` (noload: the journal is dirty), then `qemu-nbd -d`. (2) QEMU accepts the host side of a hostfwd at once, so a TCP connect proves nothing about the guest; `info usernet` shows SYN_SENT until the guest answers and ESTABLISHED after. (3) Unix socket paths are limited to 108 bytes: instance directories are named by a short hash. (4) QMP `screendump -f png` needs QEMU 7.1+. (5) `-nodefaults` removes the monitor too, so QMP is added explicitly. (6) Never `pgrep -f`/`pkill -f` a string that appears in your own command line, it kills your shell (again). (7) Tests use stand-in qemu scripts: running a script just written can fail with ETXTBSY while another thread forks, so warm them up with a retry. (8) Both sample images are Debian 10 with sshd and apache/qdPM, boot to the login prompt in about 10 s under KVM and answer on their ports within about 12 s.
