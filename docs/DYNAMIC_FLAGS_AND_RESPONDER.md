# Dynamic flags, multi-flag challenges, and Responder challenges

Status: implemented in `kymo` and `kymo-lab` 0.4.0 (see TASKS.md and MEMORY.md for the places where the build differs from this design). Scope: Kymo platform and `kymo-lab` (target version 0.4.0). Everything here is a general Kymo feature for any organizer. It is not specific to any event.

- **Part A** (sections 1 to 17): dynamic flags and multi-flag challenges.
- **Part B** (sections B1 to B13): Responder challenges and the Verifier. It builds on Part A (flags generated by Kymo and sent to the lab host) and shares the New challenge modal, so the two are built together or Part B straight after Part A.

## 1. Goals and rules

- **Dynamic flags**: a flag generated by Kymo for each instance run, injected into that instance, and valid only for the player or team that owns the run. Sharing a flag then fails and is detectable.
- **Several flags per challenge** (boot2root: `user` and `root`), submitted through the one existing input, with progress shown as "1/2 flags", and points split by weight.
- **Admin choice**: every challenge keeps working exactly as today by default (**static**). **Dynamic** is selectable only when the challenge is an instance challenge.
- **Runtimes supported now**: container images (Docker), Podman, and virtual machines from `.ova` and the other image types the VM runtime already accepts.
- **Nothing existing may break.** All database changes are additive, all new API fields are optional, and a challenge that does not opt in follows the same code path as today.

Decisions already taken: points are split per flag by weight; SSH credentials are optional and either may be declared (key preferred when both are); Kymo generates the flags and sends them in the create request; the lab host is rebuilt.

## 2. Terms

| Term | Meaning |
| --- | --- |
| Flag mode | `static` (admin types the whole value) or `dynamic` (admin types the fixed start of the flag, Kymo generates the random end per run) |
| Flag set | The one or more flags a challenge needs. One flag is the normal case |
| Run | One started instance (a row in `instance`). Restart in Kymo creates a new run |
| Run flag | The generated value of one flag for one run |
| Flag name | A short machine key (`user`, `root`, `flag`) that links a challenge flag to a place declared in the lab manifest |

## 3. Which code path a challenge uses

| Challenge | Flag mode | Number of flags | Path |
| --- | --- | --- | --- |
| Existing and default | static | 1 | **Unchanged**: `challenge.flag`, `solve`, current scoring including dynamic points and hint costs |
| New | dynamic | 1 | Same solve path, but the expected value is the player's run flag. Dynamic scoring and hints still work |
| New | static or dynamic | 2 to 8 | Multi-flag path, partial credit per flag, static scoring only (same rule as DFIR) |

Dynamic and multi-flag are refused for tournament events in this version, as DFIR plus instance already is. A tournament challenge keeps the single static flag.

## 4. Kymo: data model (migration `0032_dynamic_flags.sql`)

All statements are `ALTER TABLE ... ADD COLUMN` or `CREATE TABLE`. No `CHECK` on an existing column is touched, so no table rebuild is needed.

| Change | Detail |
| --- | --- |
| `challenge.flag_mode` | `TEXT NOT NULL DEFAULT 'static'`, values `static` or `dynamic` (checked in code and by a `CHECK` on the new column) |
| `challenge.multi_flag` | `INTEGER NOT NULL DEFAULT 0`. 1 when the challenge has a flag set of more than one flag |
| Table `challenge_flag` | `id`, `challenge_id` (cascade), `position`, `name` (a-z, 0-9, `_`, 1 to 32, unique per challenge), `label` (optional text, admin only), `value` (the whole flag when static; the fixed start, called the prefix, when dynamic), `random_len` (dynamic only, 4 to 32, default 8), `closing` (dynamic only, text after the random part, may be empty), `weight` (integer 1 to 1000, default 1) |
| Table `instance_flag` | `id`, `instance_id` (cascade), `flag_id` (cascade), `value`, `UNIQUE (instance_id, flag_id)`, index on `value` |
| Table `flag_solve` | `id`, `event_id`, `challenge_id`, `flag_id`, `participant_id`, `user_id`, `instance_id`, `points`, `at`, `UNIQUE (flag_id, participant_id)`, index on `(event_id, participant_id)`. Mirrors `item_solve` |
| `submission.flag_id` | nullable, like `item_id` |

Rules:
- Where the challenge is single, dynamic and has one flag, its row in `challenge_flag` holds the prefix, and `challenge.flag` keeps a placeholder so existing readers (bundles, listings) still see a valid value.
- Run flags **persist after the instance ends**, because a player may submit after the instance expired.
- Run flags are stored in plain text, because the check must compare them and, later, release them. The table is never exposed to players.

## 5. Dynamic flag shape and generation

A dynamic flag is **the admin's prefix followed by a random suffix that Kymo generates**:

`<prefix><random><closing>`, with the prefix and the closing both typed by the admin

- **Prefix**: written by the admin per flag, for example `KYMO{ghost_files_` or `KYMO{b2r_root_`. It is the fixed, readable start of the flag.
- **Random part**: lowercase hex from the operating system's secure random source, independent for every flag and every run. Length is `random_len`, 4 to 32, default 8 (32 bits). Players cannot predict or derive it.
- **Closing text**: written by the admin per flag, for example `}`. It is appended after the random part. The editor pre-fills it from the challenge's *Accepted suffix* as a convenience, and the admin can change it. It may be empty.
- Example: prefix `KYMO{b2r_user_`, random part `9f3a1c7d`, closing `}` gives `KYMO{b2r_user_9f3a1c7d}`.
- The result must satisfy the challenge's accepted prefix and suffix and fit `MAX_SUBMITTED_FLAG` (500). The editor and the server both check this on save: every flag's prefix must start with the accepted prefix, and its closing must end with the accepted suffix.
- Generation happens in one place in `kymo-jeopardy` (pure, unit tested) and is called from the instance start code. There are no template tokens, so no braces in a flag need escaping.

## 6. Instance start with flags

1. Kymo builds the run as today. **Before asking the lab host**, in the same write as the run row, it generates the flags of the challenge and inserts the `instance_flag` rows.
2. The create request carries a list of name and value pairs (see section 9).
3. If the lab host fails or refuses, the run is marked failed as today (free start). The unused `instance_flag` rows stay, harmless and not accepted for submission because the run never ran: a flag counts only if its run reached `running` at least once.
4. The flags are **never** included in the player view, the instance listing for players, logs or error messages.
5. The admin Instances page shows each run's flags (admin only), with a copy button, so an organizer can verify a box by hand.

## 7. Submission (Kymo)

One input and one route. Existing rate limit, attempt cap, format check and audit trail are reused.

**Single dynamic flag**
1. Collect the flags of this participant's runs of this challenge (any run that reached `running`).
2. Build a per-participant spec for each and check the submission against every one (no early exit, so timing does not reveal which run matched). Constant-time compare, as now.
3. Correct: record the solve with the existing path (`insert_solve`), so dynamic scoring and hint costs behave as today.
4. Incorrect: look the value up in `instance_flag`. If it belongs to a **different** participant's run of the same challenge, the submission is still recorded as incorrect and a **flag sharing alert** is written to the moderation audit, naming both participants, the challenge and the time. The player sees the normal "incorrect".

**Multi-flag**
1. Candidates: the flags of this challenge that the participant has **not** found yet, taken from all their runs (a flag found in run 1 and one found in run 2 both count, once each).
2. A match records a `flag_solve` row, the flag's share of the points, and the submission. The reply carries `found` and `total` and the points awarded.
3. A value that matches a flag already found replies "you already have this flag". It does not consume an attempt and is not recorded as incorrect.
4. When `found == total` the challenge reads as solved, derived from `flag_solve`, in the same way DFIR derives it from `item_solve`. No `solve` row is written.
5. Sharing detection works as in the single case.

Rate limit and the attempt cap are **per challenge**, shared by all its flags, because the input is one.

## 8. Points per flag

- A multi-flag challenge uses **static scoring**. Its points are the total.
- Each flag is worth `total × weight ÷ sum of weights`, rounded down, and the remainder goes to the flag with the largest weight (then the later position), so the parts always add up to the total exactly.
- The board counts each flag as a pseudo challenge, `FLAG_BASE + flag_id` where `FLAG_BASE = 2 << 40`, using the same mechanism as `ITEM_BASE` for DFIR. `kymo-jeopardy` does not change.
- **Hints** on a multi-flag challenge: the cost is taken from the awards in the order flags are found, until it is fully paid, and an award is never below zero. (Confirm, see section 16.)
- Editing weights after the first solve is blocked (section 11).

## 9. Kymo and lab protocol

`CreateRequest` gains one optional field:

```json
"flags": [ { "name": "user", "value": "KYMO{b2r_user_9f3a1c7d}" },
           { "name": "root", "value": "KYMO{b2r_root_44be02a1}" } ]
```

- Absent or empty means today's behaviour.
- The lab host ignores unknown fields today, so an old lab host would accept the request and **silently inject nothing**. Therefore Kymo reads the lab host's version from `GET /v1/health` and **refuses to start a dynamic or multi-flag challenge** on a host older than 0.4.0, with a clear message in the admin pages and a free start for the player.
- Flag values are never returned by any lab API response (`InstanceInfo` has no field for them) and never written to the lab host's log.
- The lab host stores the flags with the instance record in its state file (needed so a lab-side restart can inject again). The state file is written mode `0600`, owned by the service user.
- Each flag also carries `deliver`: `"inject"` (the default, section 10) or `"hold"` (Part B: the lab host keeps it and only the Verifier container can release it).

## 10. Lab host: manifest `inject` block

`inject` is optional. Without it, flags sent for that artifact are refused (400 "this image does not accept flags"), so a typo cannot silently give a player a box with no flag.

**Container and Podman images**
```json
"inject": { "flags": [ { "name": "flag", "env": "FLAG" } ] }
```
- The value is set as an environment variable at start. `env` names are validated like `env_allow` and must not collide with `env`.
- File injection into containers is not in this version: the root filesystem is read-only and writing before start needs a separate mechanism. Environment variables cover the usual case.

**Virtual machines (`.ova` and the other VM image types)**
```json
"inject": {
  "port": 22,
  "user": "root",
  "ssh_key": "/etc/kymo-lab/keys/b2r.key",
  "ssh_password": "optional-password",
  "sudo": false,
  "flags": [
    { "name": "user", "path": "/home/ctf/user.txt", "owner": "ctf:ctf", "mode": "0640" },
    { "name": "root", "path": "/root/root.txt",     "owner": "root:root", "mode": "0600" }
  ]
}
```
- **Credentials**: `ssh_key` (a path to a private key) and `ssh_password` are each optional. If both are declared the **key is used first**. If neither is declared, flags are refused. If the key is rejected and a password is declared, the password is tried and the lab host logs which method succeeded (never the secret).
- `user` must be able to write the paths. `sudo: true` runs the write through `sudo -n`.
- **When**: after the guest answers on the network (the existing readiness check), the lab host connects and writes each file. It retries with backoff until the manifest's `boot_timeout_secs`. The instance is reported **not ready** until every file is written, so Kymo never shows the address before the flags are in place.
- **How the value is written**: sent on the SSH session's standard input, never as part of a command line, so it cannot be shell-injected and does not appear in process lists. Paths, owner and mode are validated against strict patterns when the manifest loads. The write replaces the file (so it is safe to repeat) and then sets owner and mode.
- **Failure**: if injection cannot complete in time, the lab host removes the instance and the create fails. Kymo marks the run failed. It does not use the player's start budget.
- **Host keys**: the guest is a fresh copy of a known image on a private network, so the first host key is accepted. This is documented as a deliberate choice.
- **Where secrets live**: key files go in `/etc/kymo-lab/keys/` (mode `0750`, owned `root:kymo-lab`; files `0640`). A password in a manifest would be readable by every local user because manifests are `0644`, so the installer changes manifests to `0640 root:kymo-lab`, and `kymo-lab check` warns about any manifest that carries a password and is more open than that.
- **SSH client**: the pure Rust `russh` crate, so the lab host needs no extra system packages. This is a new dependency of `kymo-lab` and is the one thing I want you to approve (section 16).
- `kymo-lab check` validates the `inject` blocks: names unique and well formed, key file present and readable, at least one credential, paths absolute, ports valid. It states the problem per manifest.
- A lab-side restart re-injects the same flags from the stored record. A Kymo-side restart is a new run with new flags.

## 11. Admin API changes (`routes/admin_challenges.rs`)

Create and update bodies accept optional fields. Omitted fields mean "as before".

- `flag_mode`: `static` or `dynamic`.
- `flags`: a list of `{ name, label?, value, random_len?, closing?, weight? }`. Required when `flag_mode` is dynamic or the list has more than one entry. For a plain single static flag, nothing changes and `flag` is still used.
- Validation (all with the existing error style, one message per field):
  - dynamic needs `requires_instance`; otherwise "Dynamic flags need an instance";
  - 1 to 8 flags; names unique and valid; weight 1 to 1000;
  - dynamic values are prefixes: they must be non-empty, and prefix plus generated part plus closing must form a valid flag; static multi values must satisfy the format as today;
  - multi-flag needs static scoring and no DFIR kind;
  - the challenge must not be in a tournament event;
  - **once any run exists or any solve exists**, `flag_mode`, the number of flags, names, prefixes, random lengths and weights cannot change (labels can). Admins who need a change duplicate the challenge. This prevents a half-run challenge from ending up inconsistent.
- The list and detail responses include the new fields for admins. Player responses carry only `flag_mode`, `flags_total` and `flags_found` (section 12).
- **Event bundles** (`kymo-event` v1) gain optional `flag_mode`, `multi_flag` and `flags`. Import of an older bundle works unchanged. Export of a plain static challenge is byte for byte what it is today (new keys are written only when used). Run flags are never exported.
- A new admin endpoint lists run flags of an instance (admin only) for the Instances page.

## 12. Player side

- The challenge response adds `flag_mode`, `flags_total` and `flags_found`. Labels and names are **not** exposed.
- **Players see only the flag input**, with its placeholder, exactly as today. Nothing about the flags is shown for a one-flag challenge.
- **Several flags**: the only addition is a small progress count, `found/total` (for example `1/2`), next to the input. It is coloured with the event's selected appearance (the accent colour of the chosen theme, not a fixed colour) and turns to the theme's success colour at `total/total`. The submit confirmation reads "Flag 1 of 2 found, +40 points".
- A wrong flag reads as today. A repeated found flag reads "You already have this flag".
- The instance panel is unchanged. No flag value or path is ever sent.

## 13. Admin UI: the New challenge modal

Rules: reuse the existing components (`Section`, `Field`, `Select`, `Toggle`, `Input`), the existing validation style and the existing `Draft`/`toBody`/`problems` flow. Keep the accessible label **"Flag"** on the single static flag input (the end to end tests select it by that label). Keep the `Type` selector, its choices and its behaviour.

**Section order (new order, same sections)**

1. **Basics**: title, category, type, description. Unchanged.
2. **Instance**: the existing toggle and fields, moved up because flag mode depends on it. Unchanged content; one added hint line when dynamic flags are chosen: "The lab host must declare the flag names below in the image's manifest."
3. **Flag** (renamed **Flags** only when more than one):
   - **Flag mode**: a two-option control, *Static* (default) and *Dynamic*. *Dynamic* is disabled, with an explanation, until the Instance toggle is on and the type is Single flag.
   - **Number of flags**: a small stepper from 1 to 8, default 1. Hidden for DFIR.
   - **One static flag** (default): exactly today's fields (Kind, Flag, case sensitivity) plus the prefix and suffix. Nothing moves.
   - **One dynamic flag**: a *Flag prefix* field, a *Random length* control (4 to 32, default 8) and a *Closing* field (pre-filled from the accepted suffix), with a live example built from them (`KYMO{ghost_files_3fa91c2e}`). The accepted prefix and suffix fields stay as today.
   - **Several flags**: a table with one row per flag: *Name*, *Label* (optional, admin only), *Flag* (the whole value when static, the prefix when dynamic), *Closing* (dynamic only), *Weight*, and a read-only *Points* column that shows each flag's share of the total. The row count follows the stepper. A copyable **manifest skeleton** below the table lists the names so the lab manifest can be written without errors.
   - Validation uses the existing inline style, one message per field, shown after the first save attempt as today.
4. **Points**: as today. For several flags, scoring is fixed to *Static* with the hint "Split between the flags by weight", as DFIR shows today.
5. **Availability**: unchanged.

**After creation**
- The flag mode and set are read-only when a run or solve exists, with the reason in plain words.
- **Test the flag** keeps working for static challenges. For dynamic and multi-flag challenges it is replaced by a note: "Dynamic flags are checked against a player's own instance."
- Hints and attachments behave as today.

**Other admin screens**
- Instances page: run flags with a copy button, and the injection state of a starting instance.
- Monitor and audit: a new "flag sharing" event type with a filter.

## 14. Compatibility and what must not break

- Migration is additive; defaults reproduce current behaviour. A challenge never touched by the new controls is byte for byte the same in the database, API and bundle.
- All existing integration tests (`jeopardy`, `ops`, the tournament and DFIR tests) must pass unchanged. All existing web tests and the Playwright tests must pass unchanged. Any selector that changes is a bug in this work, not a test to rewrite.
- Old lab host with a static challenge: works. Old lab host with a dynamic or multi-flag challenge: refused with a clear message (section 9).
- New lab host with old manifests: works, because `inject` is optional.
- Installer upgrade keeps the token, certificate and manifests (as the README states), and additionally tightens the manifest file mode.

## 15. Security and failure notes

- Flag values appear only in: the database, the lab state file (`0600`), the admin Instances page, and the SSH or environment channel into the instance. Never in logs, errors, player responses, bundles or lab API responses.
- A player with root in a VM can read the file of their own flag. That is intended for boot2root: they earned it. The flag is useless to anyone else, and trying another player's flag raises an alert.
- The compare is constant time over every candidate. The existing write lock around submission is kept.
- A flag from an earlier run of the same participant (the player, or the whole team in a team event) is accepted once for its position, even after reset. This is deliberate: restarts must not cost progress. A flag from another participant's run is never accepted and raises the sharing alert. Teammates sharing a flag with each other is not an alert, because they are one participant.
- Race: the instance is not reported ready until injection succeeds, so a player never sees an address for a box that has no flag yet.
- A failed or partly applied injection removes the instance. There is no half state.
- Probing for flag names: refusing unknown names with 400 happens at create time, an admin-side error, never reachable by players.

## 16. Decisions

Settled:
1. **Hint costs on multi-flag challenges** are taken from the awards in the order flags are found (section 8).
2. **Dynamic flag shape**: the admin writes the prefix and the closing text per flag, and Kymo generates the random part between them (section 5).
3. **SSH client**: `russh` in `kymo-lab`.
4. **Player view**: the flag input only, plus a `found/total` count coloured by the selected appearance for challenges with several flags (section 12). Names and labels are never shown to players.
5. **Flags from earlier runs** are always valid, including after a reset or restart, once per flag position. In a team event the owner of a run is the team, so a flag from any teammate's run is valid for the whole team, and a flag the team already has cannot be submitted again (it returns "already have it" and scores nothing).

Left for a later version:
- Container file injection and a QEMU guest agent method.
- Dynamic and multi-flag challenges in tournaments.

# Part B. Responder challenges and the Verifier

## B1. Goals and rules

- **A Responder challenge** is an instance challenge where the player does not attack a machine, but **repairs** it: finds the weaknesses and fixes them. A **Verifier** checks the repair and, when every check passes, releases the flag. The player pastes the flag into the normal flag input in Kymo.
- **Two endpoints**: the player sees the machine's address and the Verifier's address, both reachable only through their own VPN lab network.
- **Customisable by the organizer.** The checks are written by the challenge author, always different per challenge. Kymo provides a template (a JSON description plus script skeletons) that delimits each check: its title, its language, and the function to run.
- **Opt-in.** A challenge is a Responder only if the admin ticks it. Nothing changes for any other challenge.
- **One flag per Responder** in this version. It can be static or dynamic (Part A), and the admin chooses as for any instance challenge.
- **VPN placement only.** The Verifier exists only on a private lab network. Starting a Responder on a published-port placement is refused with a clear message.
- **Target runtimes**: whatever `kymo-lab` already runs for the target (container, Podman, virtual machine). The Verifier itself is always a container, and Docker is already required on a lab host with the VPN gateway.

## B2. What the player sees

- The challenge page has the usual description, instance start button and flag input.
- When the instance is ready, the instance panel shows two rows, each with a copy button:
  - **Machine**: the address (and a port when the target is a service).
  - **Verifier**: a web address such as `http://10.77.0.43:8080`, with an **Open** button.
- On the Verifier page the player sees the challenge title, a countdown to the instance expiry, the list of check titles with a state badge, a **Verify** button with the last run time, and, when every check has passed, a flag panel with a copy button and the line "Paste this flag into the challenge page."
- Check states and their standard messages are the same for every check:

| State | Badge | Rule | Message |
| --- | --- | --- | --- |
| Fixed | Green | The check function reports fixed | Step fixed |
| Failed | Red | It reports the weakness is still there | Weakness still present |
| Broken | Amber | The health function fails, or the function crashes, times out or reports broken | Something this step depends on is broken. Restore it, or restart the instance |
| Not run | Grey | No Verify run yet | Run Verify |

- A check that was green and later fails returns to Red or Amber on the next Verify, and the flag panel disappears until every check is green again. A restart creates a new instance and a new Verifier, so everything starts clear.
- The player never sees check output, error details or script names. Those stay in an admin-only log.

## B3. Kymo data model and rules

One additive column, in the same migration as Part A if built together (otherwise `0033`):

| Change | Detail |
| --- | --- |
| `challenge.responder` | `INTEGER NOT NULL DEFAULT 0` |
| `instance.endpoints` | `TEXT` (JSON), nullable. The endpoints returned by the lab host for a run (section B4) |
| `instance.verifier_ip` | `TEXT`, nullable. The lab address Kymo allocated for the run's Verifier (section B5). It counts as in use, like `instance.lab_ip`, for as long as the run is live |

Rules, enforced by the admin API:
- `responder` requires `requires_instance`.
- A Responder has exactly one flag: `multi_flag` must be 0. `flag_mode` may be `static` or `dynamic`.
- Not allowed in tournament events (same reason as Part A).
- Once a run or a solve exists, `responder` cannot change.
- At Start, Kymo refuses a Responder if the event's instances are not on a private VPN lab network, or if the lab host is older than 0.4.0 (the version check from section 9).
- The flag is sent with `deliver: "hold"`. For a static Responder flag, Kymo sends the static value as the held flag (name `flag`). For a dynamic one, Kymo generates it as in section 5.
- The admin API list and detail responses carry `responder`. Player responses carry `responder: true` and the run's `endpoints`, never any flag.
- Event bundles carry `responder` as an optional key, written only when true.

## B4. Protocol additions

**Create request** (Kymo to lab host): the `flags` list from section 9, where each entry may have `"deliver": "hold"`. A held flag must not also appear in the manifest's `inject` list. The `lab` placement gains a `verifier_ip`: the address Kymo chose for the Verifier, taken from the same lab network and the same pool as the instance's own address. It is **required for a Responder and absent for every other instance** (so no slot is spent on instances that have no Verifier). The lab host enforces that both sides agree: a request with `verifier_ip` for an artifact whose manifest has no `verifier` block is refused, and so is a request without it for an artifact whose manifest has one. Either way a Responder cannot start without its Verifier, and an old request still works unchanged.

**Instance record** (lab host to Kymo): two optional fields are added to `InstanceInfo`:

```json
"ip": "10.77.0.42",
"endpoints": [
  { "role": "machine",  "name": "Machine",  "host": "10.77.0.42", "port": null },
  { "role": "verifier", "name": "Verifier", "host": "10.77.0.43", "port": 8080, "scheme": "http" }
]
```

- Kymo stores `endpoints` on the run and returns it in the player's instance view. The existing `host` and `port` fields stay as they are, so older web code keeps working.
- A lab host that returns no `endpoints` leaves the player view as today.
- The lab host builds the list: a `machine` endpoint for the target, a `verifier` endpoint when the manifest has a verifier, and one `service` endpoint per listed port when the manifest asks for them.
- Held flags are never returned by any lab API response.

## B5. Lab host: how the Verifier runs

For every instance whose manifest has a `verifier` block, the lab host starts a Verifier container next to the instance. Kymo does not start it and does not need to know it exists.

**Lifecycle**
1. The lab host creates the target (VM or container) and injects any `inject` flags (Part A).
2. It starts the Verifier container, attached to the **same lab network** as the target, at the address Kymo allocated in `lab.verifier_ip`. **The Verifier is handled like another instance**: Kymo takes the address from the lab network's instance slots exactly as it does for the machine (the same "next free address" logic and the same in-use accounting), the lab host only uses it.
3. It waits for the Verifier's `/healthz`, then reports the instance as ready. Kymo never shows the addresses before this.

**Addresses.** A Responder uses **two** of the lab network's instance slots (21 per network by default): one for the machine and one for the Verifier. Kymo allocates both in the same write that records the run. If fewer than two are free, the Start is refused with the existing "your private network is full, stop another instance first" message. Both are freed when the run ends (stop, expiry, failure or the reaper), and a Kymo restart is a new run with two new addresses. The Verifier address is not predictable and differs per player; Kymo shows it on the instance panel next to the machine.
4. If any step fails, everything created so far is removed and the create fails. Kymo marks the run failed and the player's start budget is untouched.
5. **Stop, expiry, a lab-side restart and reconcile** remove the Verifier with its instance. It carries the lab host's labels (`kymo.managed=lab` and the instance name), so cleanup and orphan removal find it like any container. A lab-side restart creates a fresh one.

**Container**
- Image `localhost/kymo/verifier:1`, setting `KYMO_LAB_VERIFIER_IMAGE`. The installer builds it from a `verifier/` directory in the release, as it does for the VPN gateway.
- No capabilities, no privilege escalation, read-only root, a small tmpfs for `/tmp` and for the secrets file, a non-root user, memory 128 MB, 0.25 CPU and 64 processes by default (adjustable in the manifest up to the lab host's caps).
- Attached to the lab network only. The lab network has no route to the internet or to other labs.
- The definition directory is mounted read-only. The target's address, ports, SSH credentials and the held flag are written once at start to a file in the tmpfs, mode `0400`, never passed on a command line.
- The container name is derived from the instance name (for example `<instance name>-v`) and follows the same naming rules.
- Verifier containers are not instances and do not count toward `KYMO_LAB_MAX_INSTANCES`, but they use memory: plan about 128 MB per Responder instance on top of the target's.

**Why dynamic rather than a fixed reserved address.** A fixed address per lab breaks as soon as one lab holds two Responders (a team event, or an organizer raising the concurrent instance limit). Allocating from the instance pool needs no reserved range and no special case with the VPN gateway container's address.

**Host firewall.** The Verifier port is on the container, not on the host, so no host port is opened. The installer also adds a rule that drops traffic from the lab bridges to the host itself, so a target or Verifier cannot reach the Lab API, SSH or any other host service on the bridge address. (Today the README says no host firewall rule is needed for the DHCP exchange, which is read from a packet socket and is unaffected.)

## B6. Manifest `verifier` block

```json
{
  "artifact": "ghost-files",
  "runtime": "vm",
  "file": "ghost-files.qcow2",
  "ports": [ { "name": "ssh", "port": 22 }, { "name": "web", "port": 80 } ],
  "verifier": {
    "definition": "ghost-files",
    "port": 8080,
    "memory_mb": 128,
    "cpu_millis": 250
  }
}
```

| Field | Meaning |
| --- | --- |
| `definition` | A directory name under `KYMO_LAB_VERIFIERS` (default `/etc/kymo-lab/verifiers`) holding `verifier.json` and the scripts |
| `port` | The port the Verifier page listens on (default 8080) |
| `memory_mb`, `cpu_millis` | Limits for the container, clamped to the lab host's caps |

`kymo-lab check` validates the block and the definition directory (section B7). A manifest whose definition is invalid is reported and the artifact cannot start.

## B7. The Verifier definition (written by the organizer, per challenge)

A directory, for example `/etc/kymo-lab/verifiers/ghost-files/`, holds one `verifier.json` and the scripts it names:

```json
{
  "version": 1,
  "title": "Atlas Intranet",
  "min_interval_secs": 20,
  "run_timeout_secs": 90,
  "target": {
    "ssh": { "port": 22, "user": "verify", "key": "keys/verify.key", "password": "optional", "sudo": true }
  },
  "checks": [
    {
      "id": "archive",
      "title": "Hidden in plain view",
      "language": "bash",
      "file": "checks.sh",
      "function": "check_archive",
      "health": "health_archive",
      "timeout_secs": 10
    },
    {
      "id": "credential",
      "title": "Past its expiry",
      "language": "python",
      "file": "checks.py",
      "function": "check_credential",
      "timeout_secs": 10
    }
  ]
}
```

**Fields**

| Field | Required | Meaning |
| --- | --- | --- |
| `version` | yes | Format version, `1` |
| `title` | no | Shown at the top of the Verifier page |
| `min_interval_secs` | no | Least time between two Verify runs for one instance (default 20) |
| `run_timeout_secs` | no | Cap for one whole Verify run (default: the sum of the check timeouts, at most 300) |
| `target.ssh` | no | How the scripts reach the target over SSH. Both `key` and `password` are optional. If both are declared, the key is used first and the password only if the key is rejected. The key is a path inside the definition directory. `sudo: true` runs remote commands through `sudo -n` |
| `checks[]` | yes | 1 to 20 checks, run in the order listed |
| `checks[].id` | yes | Unique, `[a-z0-9_-]`, 1 to 32 characters |
| `checks[].title` | yes | Shown to the player, 1 to 80 characters. The author is responsible for choosing a title that does not give the weakness away |
| `checks[].language` | yes | `bash`, `python` or `exec` (below) |
| `checks[].file` | yes | A file in the definition directory (no `..`, no absolute path) |
| `checks[].function` | yes | The function to run, for example `check_archive`. Letters, digits and `_`, starting with a letter or `_` |
| `checks[].health` | no | A second function in the same file, run first. If it does not succeed the check is Broken and the main function is not run |
| `checks[].timeout_secs` | no | 1 to 60, default 10 |
| `messages` | no | Optional overrides for the three player messages (fixed, failed, broken) |

**Supported languages (this version)**
- `bash`: the file is sourced and the named function is called.
- `python`: Python 3, standard library only. The file is imported and the named function is called.
- `exec`: an executable in the definition directory, in any language, built for the runner image (a static binary is best). It is run as `./file <function>`. This is how organizers use Rust, Go or anything else without changing Kymo.
- An organizer who needs more can build their own runner image (`KYMO_LAB_VERIFIER_IMAGE`) that contains the Kymo Verifier service and more interpreters.

**The function contract**
- Environment: `TARGET_IP`, `TARGET_PORTS` (comma separated, from the manifest), `SSH_HOST`, `SSH_PORT`, `SSH_USER`, `SSH_KEY_FILE` (a mode 0400 copy), `SSH_PASSWORD` (only if declared), `CHECK_ID`, and `WORKDIR` (an empty temporary directory for this check, removed afterwards).
- Helper library, installed in the runner image:
  - bash: `source "$KYMO_VERIFY_LIB"` provides `remote CMD` (run a command on the target over SSH, key first), `http_status URL`, and the result functions below.
  - python: `import kymo_verify` provides `remote(cmd)`, `http(method, url, ...)`, and the result functions.
- Result, by exit status of the function: `0` fixed (the weakness is gone), `1` the weakness is still present, `2` broken. Anything else, a crash or a timeout counts as broken. The result functions `fixed`, `vulnerable "message"` and `broken "message"` exit with the right code. The first output line (at most 200 characters) is kept as the admin-only detail.
- Checks run **one at a time, in order**, each in its own process with its own timeout, so a slow or failing check does not stop the others.
- A check that creates test data on the target must clean up after itself.
- Scripts run **inside the Verifier container**, never on the lab host and never with host credentials.

**Template and tools (shipped with Kymo)**
- `docs/examples/verifier/template/` contains `verifier.json`, `checks.sh` and `checks.py` with one worked check each, written so an author copies the directory and edits it.
- `docs/schema/verifier.schema.json` is the JSON Schema of `verifier.json`.
- `kymo-lab check` validates every definition: schema, files exist, the function names are present in the files, languages are known, key files are readable.
- `kymo-lab verifier test <definition> --target <ip>` runs a definition against a running target with no player, printing each check's state and detail. This lets an author test every check before the event, including the expected red state on a fresh target and green after the fix.

## B8. The Verifier service (inside the container)

A small web service, written in Rust and shipped as the container's main program.

| Route | Purpose |
| --- | --- |
| `GET /` | The page described in B2, server rendered, no scripts needed beyond a small refresh |
| `POST /api/verify` | Starts a run (one at a time, refused with a wait time inside `min_interval_secs`), returns the states |
| `GET /api/state` | Titles, states, last run time, and the flag only while the last run was all green |
| `GET /healthz` | Liveness for the lab host, no data |

- There is **no login**. The network is the authentication: the address is on the player's own lab network, and the VPN gateway lets a tunnel reach only its own lab. In a team event the whole team shares the lab, so teammates share the Verifier, as they share the instance.
- State is kept in memory for the life of the container. The flag is held in memory and released only when the **most recent** run had every check fixed.
- Each run is appended to a log with time, per-check state and detail. The lab host serves it to admins at `GET /v1/instances/{id}/verify-log` (lab token), and the Kymo admin Instances page shows it, so organizers can see which check a player is stuck on.
- The page is neutral and readable in light and dark, and never shows detail beyond the title and the state.

## B10. Security and failure notes

- **Isolation**: the Verifier is a container with no capabilities, a read-only root and a lab network with no route out. Author scripts never run on the host.
- **A root player can lie.** A player with root on the target can make the target answer anything. Checks that read files or run commands over SSH can therefore be fooled by a determined player. The most reliable checks exercise behaviour from the Verifier's side (for example, send the original attack request and expect it to fail). The template's README says so, and the examples show both kinds.
- **Secrets** (held flag, SSH key and password) live in the container's tmpfs and the lab host's state file (mode `0600`). They are never in logs, error messages or player responses.
- **Sharing**: the Verifier shows the flag only inside the player's own lab. A flag that is dynamic and tied to the player's run (Part A) cannot be reused by another player, and the submission check raises the sharing alert if someone tries.
- **Reach**: the target (and the player root inside it) can reach the Verifier address on its own lab network. That is harmless. Neither can reach the host, because of the firewall rule in B5, nor another player's lab.
- **Failure**: if the Verifier container exits mid-run, the lab host restarts it once. The state is lost, and the player runs Verify again.
- **Load**: Verify runs are capped by the per-instance interval and one run at a time. Each Verifier uses about 128 MB, which is part of capacity planning.

## B11. Compatibility

- Migration is additive; defaults leave every existing challenge untouched.
- A manifest without a `verifier` block behaves as before. A lab host without the Verifier support (older than 0.4.0) is refused for Responder challenges.
- A Responder on a published-port placement or in a tournament is refused with a clear message.
- Existing tests, including the Playwright tests, pass unchanged.

## B12. Out of scope for now

- More bundled languages (use `exec` or a custom runner image).
- Weights or partial credit per check.
- Several flags per Responder.
- Responders in tournaments or on published-port placements.
- A graphical editor for `verifier.json` in the admin UI (organizers edit files on the lab host).
- Windows targets (SSH based checks assume a Unix-like target; black-box checks work anywhere).

## B13. Implementation order and tests

**E. `kymo-lab`**: manifest `verifier` block and validation; Verifier container lifecycle (create, ready gating, cleanup on stop, expiry, restart and reconcile); the Verifier container at the allocated address; held flags; `endpoints` and `ip` in the record; the Verifier service and runner image; helper libraries for bash and python; `kymo-lab check` and `kymo-lab verifier test`; the verify-log endpoint; installer changes (build the image, host firewall rule, directories). **F. Tests: every rule in B3; two addresses allocated and freed together, and the "network is full" refusal when only one slot is free; held flags never listed; Responder refused on an old lab host and on a published placement; dynamic and static Responder both validate submissions correctly through Part A.

**G. Web**: Responder toggle and its locking behaviour in the modal; the two-row instance panel; the badge; the admin Verify log. Tests: `vitest` for the draft logic; Playwright for creating a Responder, starting it, seeing both endpoints.

**H. Examples and docs**: the template directory and schema, README sections for the lab host (manifest, definition, commands) and for admins.

**End to end on a lab VM**: build the lab host, install it, add a manifest with a `verifier` block and a small definition with two checks (one failing on a fresh target, one passing), create a Responder challenge, start it as a player over the VPN, open the Verifier address, press Verify to see red and green, fix the target, see all green and the flag, submit it in Kymo and confirm the solve. Then confirm another player cannot reach this Verifier address.
